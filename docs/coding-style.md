# C++ 代码规范

## 可读性和精简

- 代码首先是给人读的。流程应当清楚、短、直观；不要用额外层次、重复检查和辅助函数制造“严谨”的假象。
- 抽象必须封装真实行为、策略或差异。只改一个名字的一行转发函数通常应当删除，直接调用原操作。
- 防御性编程应当停在边界：外部输入进入系统时验证一次，对象成功构造后信任其不变量。
- 验证只拒绝明确非法、会导致当前操作无法正确继续的数据；不要把当前已知值集合当成未来协议的永久白名单。
- 不为尚不存在的需求增加兼容层、兜底分支或“以后可能有用”的封装。

## 数据库和 ORM

- 后端差异必须由 driver 或 dialect 封装。公共 ORM 调用方不得为了统一语义而拼接 PRAGMA、系统表查询或后端专属 SQL。
- `Form` 是表的长期类型化视图，不是数据库完整物理 Schema 的镜像。
- `Form::attach()` 只检查当前 Form 真正依赖的列是否存在、类型是否可用。额外表、额外列、索引、默认值、CHECK、UNIQUE、主外键和 NULL 约束差异不得单独导致 attach 失败。
- 默认 attach 不分析调用方未来会写入的具体值，不能因为两侧声明看起来不同就推断必然冲突。严格模式必须对应可静态证明、会影响所有相关读写的具体冲突类别；没有这样的分类时不先造级别 API。
- 如果物理约束是某次写操作成立的必要条件，让该操作返回数据库的真实错误；不要在 attach 时猜测所有未来操作并要求声明完全一致。
- `Form::bind()` 只用于已由调用方建立存在性不变量的数据库或事务，不偷偷执行 I/O。
- 创建接口可以验证“要创建的声明本身是否可生成”，但不得据此拒绝一个当前读写所需列均可用的既有表。
- 不为统一表象而修改数据库后端默认行为；确需某项行为时提供显式 driver option，应用不拼接对应 SQL。
- 性能策略和持久化策略（例如 journal mode）不是通用连接正确性的前置条件，不得被隐式强制。

## 错误与兼容性

- 保留底层原生错误上下文，让调用方能回答具体哪次操作、哪个字段或哪个约束失败。
- 未知枚举数值和未来新增值只要底层表示可承载，就应被保留并继续传递；只有类型、范围溢出或表示损坏才失败。
- 兼容性测试必须覆盖额外表、额外列、约束差异、缺少必需列、类型不兼容和真实写入失败。

## Neko 反射元数据

- 小型对象在不需要 tag、字段重命名或显式字段列表时，可以省略 `Neko`,`Meta` 定义。
- 一旦定义 `Neko`或`Meta`，`Object(...)` 中每个字段必须独占一行并手动对齐。
- 手动对齐的 `Neko`或`Meta` 块使用 `// clang-format off` 和 `// clang-format on` 保护。
